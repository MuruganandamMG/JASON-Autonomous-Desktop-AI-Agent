# JASON Implementation Plan

> **For agentic workers:** After explicit implementation approval, use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task by task. Checkboxes track future work; none of them is complete merely because this document exists.

**Status:** Research-backed review draft, November 1, 2026. No implementation authorization received.  
**Goal:** Build JASON, a live terminal Windows agent with three PowerShell sessions, demo-project/VS Code tools and public/demo browser automation, using Gemini free-tier AI exclusively.  
**Architecture:** One asynchronous local coordinator, explicit tool/permission and data boundaries, a shared quota scheduler, supervised shell processes and local checkpoints. The model proposes actions; validated local code executes them and verifies evidence.  
**Tech stack:** Standalone Python 3.12+ subject to wrapper compatibility, PowerShell 7, Google GenAI SDK, prompt_toolkit, Playwright Chromium, SQLite, and a verified ConPTY/Win32 adapter. Exact dependency versions are selected after approved compatibility checks.  
**Spec:** [JASON research and product design](../specs/2026-11-01-jason-design.md)

## Global constraints

- Product and terminal identity: JASON; executable/module name: jason.
- First usable release: live terminal text conversation, three independent persistent PowerShell sessions, project files/VS Code launching and browser control; broader desktop control later.
- AI provider initially Google Gemini Developer API/AI Studio; AI API budget $0/month; free tier exclusively; never activate or fall back to paid usage.
- Lite model for ordinary/light work, Flash for complex/coding/autonomous work, selected by actual free eligibility and project quota.
- Cloud inputs contain only non-sensitive public/demo content. Withhold uncertain content locally.
- Broader standing permissions are explicit scoped grants; prompt only for uncovered effects. Grants do not override data policy.
- Permission enforcement, local stop controls, operation journaling and quota admission precede executable model actions.
- Foreground runtime only in v1; shell state persists while alive, not through reboot/exit. No hard OS containment is claimed.
- No product code, scaffolding, installation, account changes or live API calls before user approval.
- Proposed implementation approval includes local milestone commits containing only this implementation's reviewed changes in the selected/new JASON repository; preserve unrelated work and review hooks. It does not authorize pushing, publishing or sending messages. This is separate from the finished agent's runtime grants for other projects.

## Review focus

1. Quota reset or network retry after a partly completed mutation must not repeat the mutation (Tasks 4 and 8).
2. User edits/cancels a task while tool arguments are streaming; stale arguments must never execute (Tasks 2 and 5).
3. Typed chat, retained history or a demo-project script contains a secret, or a child inherits the Gemini key; nothing sensitive reaches the model or child environment (Tasks 2, 5, 6 and 7).
4. One server blocks or floods output while the user types; conversation and other sessions remain usable (Tasks 3 and 6).
5. The desired local port belongs to an unrelated program; selective stop and recovery must preserve it (Tasks 6 and 9).

## Shared contracts

Future types in types.py must consistently represent:

- TaskContext: task_id, revision, project_id, grant_ids, cancellation signal and deadline.
- Action: operation_id, task_id, revision, tool name, typed arguments and declared effects.
- CommandRecipe: recipe_id, executable, argument schema, canonical cwd, reviewed script/manifest/lockfile identities and disclosed effects. PreparedCommand is emitted only after recipe/one-off approval and current policy validation; shell adapters do not consume raw model command text.
- ToolResult: operation_id, status, evidence references, sanitized summary and optional exit_code/error.
- ModelEvent: text delta, complete tool call, usage, completion or typed failure; partial arguments remain adapter-private.
- ModelRequest: route, approved context, tool schemas, output cap and task revision.
- Usage: request attempts and provider-reported token categories, with unknown fields preserved as unknown.
- QuotaDecision: admit/wait/block, reservation_id, reason and optional next eligible timestamp.

Provider interface: ModelProvider.stream(request: ModelRequest) returns an async iterator of ModelEvent; ModelProvider.cancel(request_id: str) returns a cancellation observation, not rollback. Registry dispatch: execute(action: Action, context: TaskContext) returns ToolResult only after policy and revision checks. Cancellation and status paths do not call the provider.

## Task 6: Three persistent shells and Windows process supervision

**Files:** Create shells.py, winprocess.py and tests/windows/test_shells.py.  
**Consumes:** Validated command grants, TaskContext, Store and cancellation controller.  
**Produces:** ShellManager.create(slot, cwd) -> Session; execute(session_id, prepared_command: PreparedCommand, context) -> command handle; interrupt(session_id) -> observed stop result.

- [ ] Write Windows acceptance cases for PS-1/2/3 with separate cwd/variables, Unicode/ANSI output, explicit command completion and native exit codes. A fourth shell request queues or returns a capacity status.
- [ ] Spike the chosen ConPTY wrapper, worker I/O bridge, controlled completion records and Job Object assignment before expanding functionality. Validate output pressure and crash cleanup on the actual Windows build. If this fails, revise the adapter; do not fall back to fresh processes while claiming persistent shell state.
- [ ] Implement serialized per-session commands, bounded buffers/log rotation, sanitized child environments and exclusive task ownership until all tracked foreground/background children exit. A foreground server occupies its session; a returned prompt alone does not free a session with a live background child. Reset a session before unrelated-task reassignment; uncertain ownership blocks automatic reuse. Interactive/full-screen prompts require handoff or a clear unsupported result.
- [ ] Implement graceful interrupt, the spec's 5-second grace, forced owned-job stop and a further 5-second observation window. Return shell-reset/remaining-process evidence. Preserve an unrelated process listening on a desired port.
- [ ] Add a real Windows gate: Task A launches a background child and returns; Task B cannot borrow that slot; stopping a task in a different slot preserves A. Exercise a controlled detached/untracked-child condition and verify uncertain cleanup is reported rather than silently reassigning the slot or claiming complete termination.
- [ ] Run: python -m pytest tests/windows/test_shells.py -q. Manually type into the CLI while three real shells run; stop one stubborn child and check the others and their ports. Expected: independent state, no API-key inheritance, prompt remains usable and accurate cleanup reporting.
- [ ] Review and commit only after the real Windows gate passes.
