# JASON: Windows runtime research

Researched 2026-11-01. Primary sources only. Research and proposed validation; no implementation, installation, or machine configuration changes performed.

Local preflight reported by the coordinating agent: Windows 11 Home Single Language, build 26300; about 15.60 GiB usable RAM. PowerShell 5.1 and VS Code CLI/git resolve; `pwsh` resolves only within Codex's bundled runtime, and `python` resolves to the WindowsApps alias with no `py` launcher. These observations do not establish standalone Python or PowerShell 7 installations suitable for JASON. Do not depend on another application's bundled runtime. This build is above the documented ConPTY 24H2 shutdown threshold; still validate actual wrapper behavior. No additional local hardware/private-data scanning was performed by this researcher.

Planning corrections from the reviewed proposal: capability policy and approvals must precede the first shell command, not wait for a later phase. A Notepad demo that only writes its file directly validates file editing, not native GUI automation; a later GUI milestone must invoke and verify actual application controls.

## Findings that change the blueprint

1. **Async Python is feasible, but ConPTY is not an asyncio subprocess option.** Windows `ProactorEventLoop` supports ordinary subprocesses; `SelectorEventLoop` does not. Proactor pipe adapters require overlapped handles, while ConPTY's supplied communication handles use synchronous I/O. Microsoft recommends independent channel threads to avoid deadlocks. Proposed architecture: one asyncio coordinator, with a tested native ConPTY adapter or worker threads communicating through bounded queues. Do not put blocking PTY reads on the main loop. [Python Windows platform support](https://docs.python.org/3/library/asyncio-platforms.html), [Microsoft ConPTY hosting](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session).

2. **ConPTY output is a terminal presentation stream, not structured command results.** It is UTF-8 and includes terminal control sequences; the host must interpret rendering/input. Consequently, prompt detection, regex ANSI stripping, or a quiet interval cannot reliably prove arbitrary interactive-command completion. This is an engineering inference from the documented interface. Use explicit execution records for controlled commands, and a separate interactive mode with user handoff for arbitrary prompts/full-screen programs. [Pseudoconsoles](https://learn.microsoft.com/en-us/windows/console/pseudoconsoles), [Terminal definitions](https://learn.microsoft.com/en-us/windows/console/definitions), [Virtual terminal sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences).

3. **“Persistent shell” must mean a living process, unless restart recovery is separately designed.** PowerShell variables/functions belong to its session and disappear when it ends. Environment changes normally affect that session and descendants. A fresh `pwsh -Command` for each call does not preserve state. Keep each named shell alive; serialize commands in it. A foreground dev server occupies that shell, so launch it in a dedicated managed shell/process instead of promising another simultaneous foreground command in the same shell. The scheduling recommendation is an inference. Persisted metadata/logs cannot restore arbitrary in-memory shell state. [PowerShell sessions](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pssessions?view=powershell-7.5), [Environment variables](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_environment_variables).

4. **Unlimited log collection and naive cancellation are incorrect.** Waiting without draining subprocess output can deadlock. `communicate()` drains it but buffers the result in memory and closes stdin, making it unsuitable as the sole mechanism for unlimited, persistent sessions. Windows `Process.terminate()` calls `TerminateProcess`; `kill()` is its alias, not an automatic whole-tree stop. Use continuous bounded output draining, optional rotating logs, and an explicit process supervisor. [Python subprocess contract](https://docs.python.org/3/library/asyncio-subprocess.html).

5. **Job Objects provide process/resource supervision, not a filesystem sandbox.** Ordinary `CreateProcess` descendants normally join the parent's job, with documented breakaway and alternate-launch exceptions. `TerminateJobObject` stops members; `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` can clean up when the last job handle closes. Nested jobs exist on modern Windows, but job membership/limits can conflict and must be tested. “Every possible descendant will always be killed” is too broad. Do not leak/inherit job handles accidentally. Attach a process to its job before allowing useful execution; the Win32 job-list startup attribute is a candidate, subject to adapter support. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [Nested jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs), [Startup job-list attribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

6. **“Stop this command but preserve its shell” differs from “kill its job.”** A job containing a persistent shell and children will also lose that shell on forced termination. Ctrl events are console-dependent: `GenerateConsoleCtrlEvent` targets processes sharing the caller's console, and `CTRL_C_EVENT` cannot be restricted to an arbitrary nonzero process group. Test the chosen ConPTY wrapper's actual interrupt behavior; do not assume writing a control character or Python cancellation guarantees a clean interrupt. Define graceful interrupt, bounded grace period, then forced job stop with an explicit shell-reset result. [Console control events](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent).

7. **ConPTY shutdown depends on the Windows build.** `ClosePseudoConsole` sends close events and output can continue during teardown. Before Windows 11 24H2 it can wait indefinitely unless output is closed or drained; from build 26100 it returns immediately, so returning is not proof that all clients exited. Confirm cleanup through output closure and supervised process state. [ClosePseudoConsole](https://learn.microsoft.com/en-us/windows/console/closepseudoconsole).

8. **Project scoping is an application policy until an OS boundary enforces it.** A process normally runs under its caller's security context. Its working directory does not replace that token or deny access elsewhere. npm scripts are arbitrary executable/shell commands (normally `cmd.exe` on Windows), including lifecycle hooks. Thus an allowed `npm install`, build, test, or Python script can read/write outside the project and use inherited credentials/network permissions. File-tool path validation helps only those tools. AppContainer offers OS-enforced resource controls but needs compatibility research; a separate account/VM is another architectural option to evaluate. Do not describe an ordinary user process plus cwd and allowlist as sandboxed. [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [npm scripts](https://docs.npmjs.com/cli/v11/using-npm/scripts/), [AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation).

9. **Playwright cannot promise seamless control of the user's normal Chrome profile.** Its docs disallow automating the default Chrome profile and concurrent instances sharing one user-data directory. Recommend a dedicated persistent JASON profile and explicit login by the user. CDP attachment supports Chromium only and has lower fidelity than Playwright's native connection; it requires a browser exposing a debugging endpoint, not merely any browser already open. Chrome 136+ ignores remote-debugging switches for the default data directory. [Playwright BrowserType](https://playwright.dev/python/docs/api/class-browsertype), [Chrome remote-debugging changes](https://developer.chrome.com/blog/remote-debugging-port).

10. **Native desktop automation is session/privilege dependent.** Ordinary UI Automation cannot freely drive elevated/system UI; UIAccess has signing, installation and intended-use requirements and is not a generic privilege bypass. Services run in session 0 and cannot directly interact with the logged-in desktop; Microsoft recommends a separate interactive-user component. Locked desktops, UAC prompts, and minimized RDP sessions can disrupt UI automation. Plan same-user desktop control first; require human handling of UAC and stop/pause when the desktop becomes unavailable. Do not lower UAC or promise lock-screen/unattended desktop operation. [UI Automation security](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-securityoverview), [Interactive services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services), [Microsoft UI automation failure conditions](https://learn.microsoft.com/en-us/troubleshoot/power-platform/power-automate/desktop-flows/ui-automation/uipi-issues).

## Candidate libraries, not final commitments

- `prompt_toolkit` offers `PromptSession.prompt_async()` and `patch_stdout()` so background text can appear without corrupting an active prompt. It is a reasonable minimal terminal-chat candidate. Test token streaming, multiline paste, cancellation and server logs together before selecting a fuller terminal UI. [Official prompt documentation](https://python-prompt-toolkit.readthedocs.io/en/master/pages/asking_for_input.html).
- `pywinpty` supports native ConPTY and legacy winpty and exposes process read/write/resize. It is a candidate adapter, not proof of asyncio, tree-cancellation, or shell-completion correctness. Its source includes blocking reads and a reader thread; test exact released wheels against the chosen Python/Windows version and inspect job assignment support before adopting it. [Maintainer repository](https://github.com/andfoy/pywinpty), [Adapter source](https://github.com/andfoy/pywinpty/blob/main/winpty/ptyprocess.py).

## Feasibility spikes after explicit implementation approval

1. **Shell fidelity and completion:** run two shells with separate cwd/variables, Unicode/no-newline/progress output, prompts, terminal resize, long lines, terminating/nonterminating PowerShell errors and native exit codes. Prove command boundaries despite prompt-like output. Record limitations for full-screen programs.
2. **Concurrency and output pressure:** keep a chat prompt responsive while a dev server and high-volume build run; cap memory/log retention; verify one session's blocked input/output cannot freeze others.
3. **Lifecycle:** cancel a foreground command gracefully, force-stop a stubborn child, preserve unrelated sessions, verify ports released, test shell crash and supervisor crash. Confirm job membership and absence of leftover processes on the target Windows build. Decide whether servers stop or survive JASON exit.
4. **Scope truthfulness:** in a disposable test area, demonstrate that application-only path controls do not contain an arbitrary spawned script. If hard confinement is required, prototype that OS boundary before broad shell execution and browser/IDE integration.
5. **Browser lifecycle:** dedicated persistent profile, manual login, reuse, logout, profile contention, download paths, disconnect/reconnect and intentional shutdown; do not test on a personal default profile.
6. **Later desktop phase:** same-user app controls, missing accessibility trees, focus changes, multi-monitor/DPI, lock/unlock and elevation refusal. Test pause/resume and a visible stop control. Monitoring needs separately specified capture scope and retention.

## Highest-impact user questions

1. Which Windows version/build, PowerShell (5.1 or 7), terminal app, and Python version should the first release support?
2. Does “persistent” mean across commands, closing/reopening JASON, or machine restarts? Should dev servers stop on exit or stay alive under a separate supervisor?
3. Must v1 handle arbitrary interactive programs/full-screen TUIs, or are coding commands plus prompt handoff sufficient?
4. Is project scope an agreed policy for trusted local commands, or must Windows actually prevent spawned code accessing other files/network/credentials? Is a separate account/VM acceptable if needed?
5. Is a dedicated browser profile acceptable, or is attaching to a specifically launched existing Chromium browser essential? Which authenticated sites and download/upload actions are required?
6. What should Cancel do: interrupt only the current task, stop its entire process group even if the shell resets, or stop every JASON activity? Which operations need individual approval?
7. For the later desktop/monitoring phase, what exact apps and observations are authorized, when should capture run, what should be retained/sent to the cloud, and should locked/elevated desktops always pause?

These findings establish feasibility and design constraints, not a tested implementation. Pin dependency versions only after requirements and the target OS are confirmed.
